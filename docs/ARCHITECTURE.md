# 架构与实测记录

本文记录**为什么这样设计**。所有参数都来自真实设备上的反复实测，
不是"看起来应该这样"。

---

## 1. 采集为什么必须走图像匹配

目标 App 的画面由单一 Surface（Egret / Canvas 渲染）输出，
`uiautomator dump` 拿到的层级里：

| 指标 | 实测 |
|---|---|
| 节点总数 | 9 |
| 带 `text` 的节点 | 0 |
| 带 `resource-id` 的节点 | 0 |
| `clickable=true` 的节点 | 0 |

也就是说**无障碍树里没有任何可交互控件**。基于控件 ID 的自动化在这类应用上完全失效，
只剩两条路：图像匹配（本项目的选择），或坐标盲点（作为降级）。

好消息是窗口没有 `FLAG_SECURE`，`screencap` 能拿到真实画面（不是黑帧），
所以"截屏 → 匹配 → 点击"这条路成立。

---

## 2. 取图方式的选择

同一台设备上实测四种取图方式的单帧耗时：

| 方式 | 耗时 | 结论 |
|---|---|---|
| `screencap -p` 写入 `/sdcard` | **6159 ms** | 慢在 FUSE 写盘，禁用 |
| `screencap -p` 写 `/data/local/tmp` + `pull` | 1024 + 72 ms | 可用 |
| `adb exec-out screencap -p` 直传电脑 | **1082 ms** | 当前默认 |
| `adb exec-out screencap`（裸 RGBA） | 627 ms | 最快，但需自行解码，未采用 |
| `adb shell echo`（指令固定开销） | 61 ms | 点击延迟很低 |

结论：`exec-out screencap -p` 是速度与复杂度的平衡点。

---

## 3. 点击：为什么必须是"长按"

最初用 `adb shell input tap x y`，现象是：**大约一半的点击没有生效**，
表现为"卡片打开了但又没打开"、需要点两次。

排查结论：`input tap` 的按下-抬起间隔极短，部分游戏引擎（含 Egret）
会把它判定为无效手势丢弃。

修正：统一改用

```bash
adb shell input swipe x y x y 160
```

即"在同一坐标按住 160 ms"，等价于一次真实按压。此后点击成功率稳定。

> 这也是早期"以为要点两次才能打开卡片"这个错误结论的来源。
> 真相是第一次点击被吞，第二次才生效。

---

## 4. 保存之后：输入被锁 2~3 秒

点击详情页的「保存」按钮后，图片会写入相册目录，但**接下来约 2~3 秒内所有点击无效**
（推测是 PNG 编码 + 媒体库扫描阻塞了 UI 线程）。

实测：

| 保存后等待 | 点击「关闭」是否生效 |
|---|---|
| 0.6 s | ❌ |
| 1.5 s | ❌ |
| 2.6 s | ✅ |
| 4.0 s | ✅（当前值） |

修正：保存后固定等待 4.0 秒再操作。这是"慢一点但正确"的取舍。

---

## 5. 成功判据：只认文件

每次保存前记录 `/sdcard/Pictures` 的文件名集合，保存后轮询（每 300 ms，最长 10 秒）：

```python
before = set(pictures())
hold(camera_button)
new = [n for n in pictures() if n not in before]
```

只有出现新文件才算成功。这样做的价值在调试期非常明显：
它能区分"点了但没生效"和"点了且成功"，而前者如果被当成成功，
会导致后面整条流水线静默错位。

## 6. 从网格模式到滑扫模式

### 网格模式的失败

最初按 6 个格子的坐标逐页点选：

```
第 N 页 → 格 1..6 → 翻页 → 第 N+1 页
```

踩到的问题：

1. **页码推算与真实页码不一致**：App 重启后相册回到第 1 页，
   而脚本按"已完成张数"推算当前页 → 打开的是错误位置 → 读到重复内容。
2. **点击选中态难以验证**：卡片是"先选中、再点一次打开"，
   第一次点击被吞时，第二次会打开**上一次选中的那张**，导致"不同格子读到同一张"。
3. 排序方式（按时间 / 按内容）会改变内容顺序，进一步放大上述问题。

### 滑扫模式

关键发现：**详情页支持左右滑动切换相邻卡片**。

于是采集退化为：

```
打开第一张 → [保存 → 左滑] × N
```

好处：

- 不再需要网格坐标、页码、排序方式
- 不再有"点错格子"这一类错误
- 每张只有两个固定动作，状态机极简

---

## 7. 如何区分"滑不动"与"到头了"

这是最容易误判的地方。早期用"画面连续 3 次不变"判定到达末尾，
结果在第 18 页就误报"完成"——实际是连续三次滑动被吞。

现在的做法：给每一帧计算**联合签名**

```
frame_sig = sha256( 明信片画面区域 + 右下角页码区域 )
```

| 签名 | 含义 | 处理 |
|---|---|---|
| 完全不变 | 滑动没生效 | 重试滑动（最多 8 次），不计入"末尾" |
| 变了，画面哈希也变 | 正常换卡 | 继续 |
| 变了，但画面哈希不变 | 页码变了、画面一样 → 相册里确实收录了同一张 | 正常跳过 |

只有在**连续 8 次滑动无效**且**已走过 ≥480 个位置**时，才判定到达末尾；
否则报"卡在某个位置"并保留进度。

---

## 8. 画面淡入导致的"假重复"

打开卡片后，相框与工具栏是立刻出现的，但**明信片画面有一个淡入过程**。
若在 1 秒后就截图，会截到上一张的残影，导致：

- 两张不同的卡片得到相同的画面哈希
- 被误判为"重复"，从而**跳过了一张没采到的卡**

修正：打开卡片后连续截两帧，只有两帧哈希一致才认为渲染完成。

---

## 9. 其他环境干扰

| 干扰 | 现象 | 处理 |
|---|---|---|
| **屏幕休眠** | 截图全黑 | `svc power stayon true` + 启动前唤醒 |
| **系统锁屏** | 点击落在锁屏，后续全错 | 检测 `isKeyguardShowing=true` 后停止并提示人工解锁 |
| **通知横幅** | 盖住页头，模板匹配失败 → 误判"不在相册" | 判定区域下移到排序按钮行；判失败时重试 3 次 |
| **App 被系统回收** | 界面回到主界面 | 采集前强制冷启动到已知状态 |
| **USB 掉线** | `adb` 报 `no devices` | 停止并保留进度 |

## 11. 数据模型

`archive/manifest.json` 是唯一索引，图片文件本身是唯一真源：

- 去重键：`sha256`（文件字节）
- 画面判重键：`sha256(明信片区域像素)`（运行期，不落盘）
- 续跑游标：`probe/sweep_state.json` 的 `processed`（已走过多少个位置）
- 归档序号：`seq`，与文件名前缀一致

设计原则：**清单可以重建，图片不可再生**。
`fix_archive.py` 正是基于这一点——扫描目录里的实际文件重建整个清单。
